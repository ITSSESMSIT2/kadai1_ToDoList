# kadai1_ToDoList

岡本の課題①ToDoリスト作成です。

## 【機能概要】

ユーザーがフォームに入力した**タスク名**、**期日**、**ステータス**を受け取り、画面下部の**タスク一覧**に表示。さらに、そのタスク一覧から**削除**および**変更**が自由に行える。

フォームの入力は、それぞれ

- タスク名：テキスト
- 期日：カレンダーから選択
- ステータス：プルダウン形式で、**未対応**、**処理中**、**完了**の3項目から選択
  という形式で受け取る。

また、受け取ったそれぞれの要素にIDを付与し、配列に格納しており、
ユーザーが削除や変更を行うと、配列内でも情報が更新される。

## 【ファイル構成】

- app.js
  実際の機能を構成しているjsファイル。入力値の保存、表示、削除、変更はここで行う。
- index.html
  ユーザーに表示されるページの内容を構成しているHTMLファイル。
  第1回PR時点では必要最低限の表示要素を実装。
- index.css
  index.htmlの見え方を構成しているファイル。文字の間隔や色などはここで設定する。
  第1回PR時点では、ヘッダー、新規タスク追加のパネル、タスク一覧のパネル、箇条書き項目の先頭につく「・」の削除、背景色の変更のみ実装。

## 【工夫した点】

- alertの利用
  必須項目であるタスク名の入力が空欄もしくはnullだった際に、ページに「タスク名は必須項目です」と表示するアラートを追加。
  ユーザーがより可視的に必須項目を理解できるようになった。
- ヘッダー、パネルの実装
  必要最低限のCSSの実装の中で、ヘッダーとパネルを優先し実装した。
  入力する箇所、表示・変更・削除する箇所を明示的に分けておくことで整いきっていないページの中でも、機能を比較的明示することが可能となった。
- 配列へのliの格納
  こちらに関しては問題もはらんでいるので一概に利点とはいいがたい。
  しかしながら、配列の中に、入力要素を書式ごと格納することで値同士の一致の比較が行いやすくなった。

## 【詰まった点・調べたこと】

### CSS

- paddingの設定
  数字が一つであれば上下左右すべてに適用。二つであれば一つ目を上下に、二つ目を左右に適用。
- li項目の「・」の消し方
  list-style:none;で実装できる。
- figmaでのpaddingの確認方法
  altキーを押しながら確認したい要素にカーソルをあてる。

### HTML

- selectの記述方法
  <select>の中に<option>を記述し、そこにプル団メニューに表示したい文字列を入れ、js内で利用したいvalueも<option>に設定すればよい。
- <div><span>の違い
    <div>は同じ行に要素を持つことができないブロック要素、<span>は同じ行の中に複数要素を持つことができ、その要素同士を区切るインライン要素。
- js、CSSの接続方法
  jsは<body>末尾(<head>でも可)に<script src="○○.js">を記述。
  CSSは<head>に<link rel="stylesheet" href="○○.css">を記述。

### JavaScript

- addEventListerner
  第一引数の動作が行われたら、第二引数の関数を、指定した箇所(.addEventListernerの前に指定した項目)で行うもの。
  そのため、addEventListernerの前に来る項目はformとは限らない。
- img.src
  単にimg要素をHTMLにcreateElementしても画像にはならない。
  接続には.srcを利用し、使いたい画像の場所を指定することで初めて画像が表示される。
  今回の場合は同ディレクトリ内に画像があるため単にVector.pngの指定で解決している。
- オブジェクトの記述
  変数とオブジェクトの違いが怪しかった。複数の項目をconst変数内に収めることをオブジェクトが実現している。
- js内での<option>の作成
  作成した<option>を<select>の中に.addすることで作成できる。
- innerText、innerHTMLの違い
  innerTextは中の文字列だけを変更する。
  対して、innerHTMLはHTML要素ごと変更する。
  これらの要素は、既存の要素の上書きを行うものであるため、特にinnerHTML要素を利用する際は表示が崩れていないか注意する必要がある。
- **appendChild**
  どの要素の中に、何を子要素として格納するのかを意識しながら作成する必要があった。
  その階層の理解に時間がかかってしまったことが、今回期日を大幅に遅延した要因の一つである。
  解決策として、逐一console.logで現在操作している/操作したい要素の中身を確認すること、また一旦HTML形式で求めている形をメモに起こすなどが挙げられる。
- console.dir
  nodeNameなど、その要素が持つ内容をより詳しく参照したいときに利用する。
  console.logが要素の中身を見るものだとすれば、console.dirはその要素の持つ性質、属性のようなものを見るものだと理解している。
- **findIndex**
  findIndex()の中にはboolean式で値を返す関数を入力しておく。
  指定した配列の中で、その関数がtrueになる最初の項目のインデックスを呼び出す。
  今回は == を利用したが、不等式も利用できるため、Indexof（完全一致）よりも柔軟に利用できる。
- **配列と表示の一致**
  特に詰まった項目。
  削除機能、変更機能を実装するにあたって最大の難点は、一覧表示される内容と配列の内容を一致させ、連動させることであった。
  当初は、CSSでの表示のことを考え、各入力要素同士を<span>で区切り、それを<div>に格納、さらに大きな<div>の中に収めるという手段を取っていた。
  しかしながら、その方法での実装を行うと親要素の指定が非常に煩雑になること、また宣言する変数の量が膨大になるという問題があった。
  そこで<ul>および<li>を実装することによって、コード量が大幅に減少し、配列の中にも<li>を格納することで解決した。
    <ul>にイベントを設定、指定したイベント(画像へのクリック、プルダウンの項目変更)が起きれば<li>を軸に操作を行うように変更した。
    ここにおいて、targetの親要素とaddEventListernerの指定要素の違いに混乱し非常に時間がかかってしまった。
    今回の場合、targetに指定しているのは、<li>の中の子要素である。そのため、target.parentElementは<li>。
    しかしながら、イベントデリゲーションを活用し、どの<li>に対しても同じ動作が起きてほしいためにイベントの起点は<ul>となっている。
